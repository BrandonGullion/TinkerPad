# 04-10 · F5 runs the playground

**Phase:** 4 · **Size:** S · **Crate/area:** `ui/` (commands), `tinkerpad-app` · **Depends on:** 04-03
**Design:** PLAN.md §1 (LINQPad as the model), DEBUGGING.md, 06-05

## What

Pressing F5 runs the playground in the active tab, exactly as `Mod+Enter` does
today. `Mod+Enter` keeps working. F5 never reloads the window.

## Why

F5 is the run key in LINQPad, the tool this one is modelled on, and the
debug-or-run key in Visual Studio and VS Code. People reach for it without
thinking, and right now it does nothing they meant.

What it does today hasn't been checked, and that is the first thing to find
out. Nothing in `ui/src` or `tinkerpad-app` handles F5 or turns off the
webview's own browser shortcuts, so on Windows WebView2 (and possibly the
others) F5 very likely **reloads the page**. That would drop the output pane,
detach the run in progress from the UI, and rebuild every tab from the session
file. Autosave means code shouldn't be lost, but a reload is still the wrong
answer to "run this".

## Current state (2026-10-25)

- `run.start` is bound to `mod+enter` in `ui/src/commands/catalog.js`.
- A command has **one** default binding (`key?: string`), and
  `keybindings.toml` maps a command id to one string. Making F5 the binding
  would mean losing `Mod+Enter`, which is in every self-test and probably in
  people's habits already.
- 06-05 (not started) plans F5, F9, F10 and F11 for the debugger and says to
  "let the catalogue sort out collisions". This item takes F5 first, so that
  collision has to be settled here, not left for 06-05 to find.

## Out of scope

The toolbar's Run button (04-11). Any debugger behaviour (06-05). Cancelling a
run with a function key: `Mod+.` stays the cancel key. If `Shift+F5` for cancel
is wanted, decide it together with 06-05, which may want `Shift+F5` for "stop
debugging".

## Gotchas

- How browser shortcuts are turned off differs per platform. On Windows it's a
  WebView2 setting (`AreBrowserAcceleratorKeysEnabled`), which Tauri may or may
  not expose for the version in use. On macOS and Linux, a `keydown` handler
  calling `preventDefault()` early may be enough. Check each one; don't assume.
  Platform-specific Rust only goes in the modules AGENTS.md lists.
- CodeMirror sees the key before the window does when the editor has focus.
  Make sure F5 isn't handled twice (two runs) or swallowed by the editor's
  keymap (no run).
- On macOS laptop keyboards F5 means `Fn+F5` unless the user changed that.
  Fine, but it's why `Mod+Enter` has to stay.
- Holding F5 down auto-repeats the key. Starting a run while one is going
  already means "run again", so check that repeated presses don't queue a
  pile of runs.

## Results

Implemented 2026-10-26.

**What F5 did before.** Found from the sources, not from a key press (this
machine's rules forbid sending real keystrokes; see "Open" below):

- **Windows:** wry 0.57 builds WebView2 with `browser_accelerator_keys: true`
  ("This is WebView2's default behavior"), and Tauri 2.12 has no setting or
  builder method that turns it off. So F5, `Ctrl+R` and `Ctrl+Shift+R` reloaded
  the page. Nothing in `ui/src` cancelled them.
- **macOS:** the app sets no menu, and WKWebView has no reload shortcut of its
  own (Safari's comes from its menu), so F5 and `Cmd+R` most likely did
  nothing.
- **Linux:** wry's WebKitGTK code binds no keys, and WebKitGTK has no reload
  shortcut of its own (the browsers built on it add theirs), so most likely
  nothing either.

Either way F5 never ran anything.

**Several bindings per command.** `key` in `catalog.js` is a string or a
list; `defaultBindings()` always returns lists. In the registry,
`bindingsFor(id)` gives them all, and `bindingFor(id)` the first, for tooltips.
`commandFor` matches any of them, the conflict check looks at each one, the
editor keymap gets one CodeMirror binding per key, and the palette and
`docs/KEYBINDINGS.md` show them all (`Ctrl+Enter / F5`). `keybindings.toml`
takes a string or a list. The core now sends lists (`Bindings` is
`BTreeMap<String, Vec<String>>`), with blanks dropped, so `""` and `[]` both
unbind.

**F5 everywhere.** `run.start` is `["mod+enter", "f5"]`, so Mod+Enter keeps its
place, first. A new catalog flag, `anywhere`, lets a command's unmodified keys
work in a text field; only `run.start` has it, because F5 types nothing. In the
editor, only the Enter binding gives way to an open completion popup; F5 runs
whatever is showing.

**Reload keys.** `isReloadKey` in `main.ts`: F5 always, and `Ctrl+R`/`Cmd+R`
(with or without Shift) except in a dev build. It is cancelled in two places:
in the capture phase on `window` for anything outside the editor (before the
tab-rename input, which stops propagation, can hide the key), and on the way
out for the editor. **The item's gotcha had the order wrong:** the window's
capture-phase handler sees a key *before* CodeMirror does, and CodeMirror
skips any event already cancelled (`runHandlers` checks `defaultPrevented`).
Cancelling F5 early would have stopped the editor's binding from running.

**Auto-repeat.** A repeated F5 (or Mod+Enter) keydown is swallowed by the
window's handler before CodeMirror, so holding it down is one run.

**Tests.** Two new Rust tests in `keys.rs` (a list is tidied and binds every
key, a list of non-strings is refused) and the old ones updated; seven pass.
The `keys` self-test scenario gained eight checks, all passing locally on
Windows (debug build, `tauri build --debug`, the same build CI uses):

```
PASS F5 runs the playground from the editor, and doesn't reload
PASS F5 runs it from the output pane too
PASS and from a text field
PASS an auto-repeated F5 doesn't start another run
PASS the palette shows every key a command answers to
PASS a list in keybindings.toml binds every key in it
PASS Mod+R doesn't reload the window in a built app
PASS F5 with no playground open does nothing, and doesn't reload
```

"Doesn't reload" is checked as "the keydown was cancelled", not with the marker
the item suggested. A synthetic event can never reload the page, so a marker
would pass whatever the code did. A cancelled keydown is what stops a real one.
The `layout`, `run`, `tabs`, `library-panel`, `locked` and `annotations`
scenarios still pass (79 checks).

**`keys` now runs in CI.** It never did. It's added to the language-server
step on Linux and macOS, which already has the `node-check` test plugin it
needs.
